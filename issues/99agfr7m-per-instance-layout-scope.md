## 问题描述

位置：`src/emulator.js` 的模块级变量 `package_scope` 和 `#get_scope`；规范 §4“布局登记域”、§5 `scope`；设计中的“绑定”“登记域”两条（a60df57 引入）。

现在第一个取得登记域的模拟器把整个包绑定到该登记域，直到进程结束：

- 之后的描述指定其他登记域，构造时报错 `scope X: the package uses scope Y`。
- 带布局（`layouts`、`item_tables`）的描述注册成功后，同一进程中不能再构造：同一登记域只能注册一次，第二次构造报登记域已注册。

设计意图应当为：一个模拟器实例只绑定一套布局；有多个实例时各用各的，互不串用。这样能简化布局的描述和实现模拟器实例之间的分离｡

影响：调用方无法在同一进程中多次用独立布局的描述构造模拟器。例如想模拟出多个布局有微小差异的多型号设备。

## 解决提案

方向：登记域的绑定归实例所有，去掉模块级的 `package_scope`；同时让布局相同的描述复用同一个登记域，因为多个模拟器常常用同一套布局，而布局注册后不再改变，实例之间的分离靠各自的 Ldata 块，不靠登记域。

- 布局特征值：描述列表中各描述的布局内容合并后的哈希，只取 `layouts` 和 `item_tables`，不取 `scope`、`blocks`、`servers` 及其他根键。
  - 合并：`item_tables` 按表名合并为一个映射；各描述的 `layouts` 连成一个列表后排序。`layouts` 是集合，顺序无意义（每个布局只由它自己的条目表构建，重复列出是 layout-data 的错误），描述列表的顺序也就不影响特征值。重名等错误不在此判断，交给注册。
  - 规范化序列化：`layouts` 取合并时排好序的列表；`item_tables` 中对象的键递归排序，数组保持顺序（条目表中条目的先后就是布局结构）；JSON 不能表示的值（如 `bigint`）明确编码。再取 SHA-256。
  - 要求：特征值相同则注册结果相同；反之不要求。省略默认值与显式写出默认值、未被引用的条目表等造成的漏判，只是多建一个登记域，不会绑错。
- 进程内维护一个 `Map`：布局特征值 → 已注册的登记域（及其注册结果）。只登记注册成功的登记域。
- 描述带布局时，先按特征值查找：
  - 找到：描述没有 `scope`，或 `scope` 与该登记域同名，就直接绑定它，不再注册；`scope` 是其他名字则报错（一个登记域只有一个名字）。这是描述之间的配置冲突，不是可以重试绕过的状态：错误信息指明已注册的登记域名，提示改正描述（使它们给出相同的 `scope`，或都不给）后重启程序。
  - 找不到：以 `scope` 为名称新建登记域并注册；没有 `scope` 时名称为 `s` 加特征值的前 8 位十六进制数字，同一套布局每次运行都得到同一个名字。登记域已存在（`scope` 指定的名字已被调用方或另一套布局占用，或自动名字的前缀碰撞）时，由 layout-data 报登记域已注册；`Map` 以完整特征值为键，碰撞只会报错，不会绑错。
  - 因此同一份描述可以在同一进程中构造任意多次，各次共用一个登记域。
- 描述不带布局时，必须给出 `scope`，绑定 `get_scope(scope)`；登记域不存在、或没有给出 `scope`，都是错误。
- 调用方通过实例的 `scope`、`layouts` 属性取得它的登记域和布局，不靠登记域名查找；`layouts` 的键顺序无意义。

不采用的做法：

- 特征值包含 `scope`：只多出“内容相同、名字不同就再建一个内容相同的登记域”，而名字本身已由 layout-data 保证唯一，不增加任何区分能力。
- 每个实例都新建登记域、带布局时禁止 `scope`：同一套布局重复注册，且调用方无法给登记域命名。
- 以编译后的布局取特征值：要先注册才能得到，失去复用的意义。

需要同步修改规范 §4、§5 和设计（中英文）、类型声明，以及相应的测试。0.2.0 尚未发布，可以并入。

## 裁定

接受，按解决提案实施。包级绑定使同一份带布局的描述在一个进程中只能构造一次，与“一个实例绑定一套布局”的设计意图不符；按布局特征值复用登记域，既让实例各自绑定，又不重复注册同一套布局。
