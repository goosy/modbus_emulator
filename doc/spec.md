# modbus-emulator Specification

> Chinese edition: [spec.zh-CN.md](spec.zh-CN.md). Keep the two in sync.

## 1. Goals and Scope

modbus-emulator is a Modbus device emulator library. It provides Modbus slave services to the outside, and exposes the data through the Ldata / Ltag API of [layout-data](https://github.com/goosy/layout-data/blob/main/doc/spec-data-api.md), so that callers can apply extra computation to emulate the running of a device.

- Slave transports: Modbus TCP, RTU over TCP, Modbus UDP, RTU over UDP, RTU (serial port).
- One emulator can provide several services at the same time, sharing the same set of data blocks.
- It is published as a library. A controller or similar program can use its server part to publish its own data blocks to a host (HMI/SCADA).

Out of scope: the Modbus master (client), the business logic of a device (implemented by the caller through Ldata), and the output of diagnostics (the package emits events, and the caller decides what to do with them).

## 2. Terms

| Term | Meaning |
| --- | --- |
| Block | A named data block (Ldata), laid out in bytes by its layout and placed at a byte offset of a unit |
| Unit | A slave address identified by a unit id, which usually stands for one device or a group of process values. A unit can hold several blocks, each in a different byte range, and serves them in one byte order, the byte order of the device |
| Byte order (endian) | The order in which a device stores the bytes of a multi-byte value: `BE`, `LE`, `BEBS` or `LEBS`, the device byte orders of layout-data (`Endian`) |
| Unit map (`Unit_Map`) | The mapping from unit ids to blocks and their byte ranges, with the byte order of each unit |

## 3. Address Mapping

- Layouts and data blocks are static once loaded. Each `load` of the emulator adds blocks, services and layouts, and none is removed or changed afterwards. A running service cares only about the values, and does not handle changes of the data blocks.

- The content of a block is kept in big-endian (layout-data keeps one canonical copy of the data). What a unit serves is the IO buffer of each block: its bytes reordered in the byte order of the unit (`BE` by default), as the `load_tag` / `store_tag` and `Layout#io_index_table(endian)` of layout-data order them; the data a master writes is converted back to big-endian, then written to the block.
- Register `addr` corresponds to byte `addr * 2` of the unit.
- Coil `addr` corresponds to bit `addr % 8` of byte `addr >> 3` of the unit.
- Holding registers and input registers have the same content. Registers and coils are readable, and writable unless they are read-only.
- Read-only points: a placement of a block may declare the whole block or some of its tags read-only ([spec-descriptions.md](spec-descriptions.md)). The declarations of the blocks of a unit make its read-only bits, in the bytes of each block: every bit of a block declared read-only as a whole (`all`), padding included; the bit of a read-only Bool; every bit of the bytes a read-only tag of another type occupies (a composite word, Byte, Int, Real and so on), so the coupled bits of a read-only composite word are read-only too. The other bits, padding included, are writable.
  - FC 5 / FC 15: a request that writes a read-only bit is refused as a whole.
  - FC 6 / FC 16: a request that writes a register with a read-only bit in its 16 bits is refused as a whole.
  - So a register shared by a read-only tag and a writable tag cannot be written by FC 6 / FC 16, while the bits of the writable tag can still be written by FC 5 / FC 15, several consecutive bits of one FC 15 included; and a read-only tag that spans registers refuses an FC 16 that writes only one of them.
- A refused request reads or writes no point, and is answered with exception 0x02 (Illegal Data Address). A refusal is a normal answer of the protocol, not an error of the handler: es-modbus emits no `handler_error` for it. On a serial bus, a refused broadcast (unit 0) is not answered, as no broadcast is, but its write is refused all the same.
- Writes go through the write methods of Ldata, so the `change` and `write` events of the block fire as usual.
- An FC 16 / FC 15 request is atomic: each block it reaches is written once, emitting one `write` and one `access` of kind `write`; when a write fails midway, every block reached is restored and the master gets exception 0x04. FC 6 / FC 5 write one point. This is done by the handler, so a server assembled with `create_handler` behaves the same.
- A read request emits one `access` of kind `read` per block it reaches, naming only the tags read; for coils, only the Bools of the bits read.
- An error thrown by a listener of a block (`change`, `write`, `access`) when a request is committed neither undoes its writes nor affects the other blocks: the master gets a normal response, and the handler emits `listener_error` with `{ block, error }`.
- An address in a unit with no block is unmapped. By default it reads as 0 / false, and a write to it is ignored. No exception is returned, so a read or a write across a gap still succeeds, and the handler emits `unmapped` for the unmapped points (see Events).
  - A unit may refuse them instead (`unmapped_read`, `unmapped_write`, [spec-descriptions.md](spec-descriptions.md)): with `unmapped_read: refuse`, a read request (FC 1 / 2 / 3 / 4) that reaches an unmapped address of the unit is refused; with `unmapped_write: refuse`, a write request (FC 5 / 6 / 15 / 16) that does is refused. The two are independent, so a test can refuse the writes and keep the polling of a master succeeding.
  - `unmapped` is emitted only for a request that succeeds: a refused request emits `request_refused` instead (see Events).
- A unit id that a service does not answer is answered with exception code 0x0B by es-modbus over `tcp` and `udp`, and not answered at all on a serial bus (`rtu`, `rtu_over_tcp`, `rtu_over_udp`). An illegal function code, an illegal quantity, or an address out of range is answered with 0x01 / 0x03 / 0x02.
- On a serial bus (`rtu`, `rtu_over_tcp`, `rtu_over_udp`), unit 0 is the broadcast address: es-modbus executes the writes to it and never answers, so the blocks of unit 0 cannot be read through such a service. Units 248 to 255 are reserved on a serial bus. A service of these protocols that answers unit 0 or a unit from 248 to 255 gives a `warning` event of the emulator (see Events); it is not an error.

## 4. Interface

- `Modbus_Emulator(scope)`: the main constructor. It creates an emulator without blocks and services, so that listeners can be attached before anything is loaded. `scope` (optional) is the name of the layout-data scope the descriptions are loaded into, `modbus_emulator` by default; a name that is not an identifier throws the error of `create_scope`.
  - `load(sources)`: loads descriptions, and may be called any number of times. `sources` is a source or a list of sources, read together; each source is a description file (a path or a `file:` URL, [spec-descriptions.md](spec-descriptions.md)), which the package compiles with `desc_file`, or a `Description` of layout-data, compiled by the caller with the forwarded `desc_file` or `yaml`; the two may be mixed in a list. Any other value is not a source. Description files serve the end users, who write configuration files; a `Description` serves the programs that generate their descriptions. The descriptions give the layouts, the blocks to create, the units that place them and the parameters of the services, and `load` builds the blocks, the units and the services from them, without starting the services. It returns `{ blocks, servers }`: the blocks (a map from block names to Ldata) and the servers this call added. A load is checked against the emulator as a whole: a block name of the emulator, a unit of an earlier load and a port of an earlier service are errors, and the units of `unit_ids` are the ones of the emulator once loaded. A service without `unit_ids` answers every unit of the emulator, including the units of later loads.
  - An object of the shape of a description is compiled with `yaml(JSON.stringify(object))`, as JSON is YAML 1.2. YAML text has no file, so its `imports` take absolute paths or `file:` URLs.
  - `blocks`: a map from block names to Ldata. `block(name)` gets one block. `unit_map`: the unit map. `servers`: the server instances, an array whose item `i` is the service entry `i` of the descriptions loaded (the loads in order, the sources of a load joined in order); the `name` of each server is its label, its place and address in the description such as `servers[1] (modbus://0.0.0.0:503)`, so a server can be found by name (`servers.find((server) => server.name === ...)`). `scope`: the layout-data scope the descriptions are loaded into (read-only). `layouts`: the layouts of the descriptions in that scope, by name (read-only). The order of its keys has no meaning. `handler`: the handler shared by all the servers.
  - `start(options)`: starts the services that are not running: all of them at the first call or after `stop()`, and the services loaded since the last call otherwise; a running service is not restarted. An emulator without services rejects with an `Error`. Before it starts any service, the emulator holds its block names again (see Layout scope below): when the layout of a block holds its name for another Ldata, it rejects with an `Error` whose `errors` property lists every conflicting block, starts no service, binds no name, and leaves the running services as they are. By default it is all or nothing: when any service fails to start, all services are stopped, while the block names stay held, so a resolved `start()` means that all of them run and a rejected one that none runs. With `{ partial: true }` it starts what it can, and the services that started keep running. In both modes a failure rejects with an `AggregateError` that lists every failed service: each item is an `Error` whose message starts with the `name` of the service, such as `servers[1] (modbus://0.0.0.0:503): ...`, with the original error as its `cause`.
  - `stop()`: stops all services, and gives the block names back to their layouts (see Layout scope below). The blocks keep working, and `start()` serves them again.
  - Layout scope: the descriptions name no scope; the scope is chosen in code. `load` loads the descriptions into the scope of the name `scope`, created when it does not exist (`get_scope` / `create_scope` of layout-data), which keeps the layouts apart from the scopes of the caller and of other libraries that use layout-data. Loading is the `load` of layout-data: in a scope a layout of the same name and structure as one already there is shared, and a layout of the same name and another structure, or of the same structure and another name, is an error; emulators of such layouts are given different scopes. Each block is an Ldata created by its layout, which holds the block name: the same block name of the same layout is an error until the emulator that holds it has stopped (`stop()`). `start()` binds the names given back by `stop()` to their layouts again, so the names of an emulator are held from `load` to `stop()` and whenever its services run, and a failed start gives none back; serving blocks of the same name in one scope from two emulators at once is a configuration error, which different scopes avoid. So another emulator can load a description in one scope after `stop()` of the earlier emulator, and any number of emulators can load it at once in different scopes. The emulator keeps its blocks after `stop()`, so loading a block of the same name into it is still an error.
  - Invalid sources throw an `Error` whose `errors` property lists all violations: those of this package, those of the `load` of the scope, and those of `desc_file` for the description files, which name the file (a file that cannot be read is one of them). A value that is neither a description file nor a `Description` is one of them too. The errors of compiling a `Description` are thrown by `desc_file` or `yaml` when the caller compiles it. A load that fails changes nothing: the blocks, the unit map, the services, the layouts of the emulator and the scope are left as they were before the call.
- `create_tcp_server(unit_map, { host, port, rtu, unit_ids, handler, name })`: creates a Modbus TCP service. `host` defaults to `0.0.0.0` and `port` to 502, an integer from 1 to 65535 (otherwise a `RangeError`); `unit_map` is required. With `rtu: true` it uses RTU frames on the TCP socket (RTU over TCP). It returns the es-modbus `Modbus_Server`, not started.
- `create_udp_server(unit_map, { host, port, rtu, unit_ids, handler, name })`: creates a Modbus UDP service, with the options and defaults of `create_tcp_server`; `host` is the address its UDP socket binds. With `rtu: true` it uses RTU frames in the datagrams (RTU over UDP). It returns the es-modbus `Modbus_Server`, not started; the socket is bound at `start()`.
- `create_rtu_server(path, unit_map, { baud_rate, parity, data_bits, stop_bits, unit_ids, handler, name })`: creates an RTU slave on a serial port. `unit_map` is required. The defaults are 9600, `none`, 8 and 1 for `baud_rate`, `parity`, `data_bits` and `stop_bits`. It returns a `Modbus_Server`, and the port is opened only at `start()`.
- `unit_ids`: optional, the unit ids a service answers. When it is omitted, the factory copies the unit ids of `unit_map` at the creation of the service. From then on the list belongs to the service and is independent of the unit map: `attach_unit` changes only the unit map and has nothing to do with the units a service answers. To add units to a service (or remove them), call `set_unit_ids` of its `Modbus_Server`. A unit id outside the list is answered with exception code 0x0B by es-modbus.
- `handler`: optional, the handler to serve (the result of `create_handler`). Servers of one unit map can share one. By default it is built from the unit map.
- `name`: optional, the `name` of the `Modbus_Server`, which identifies it in events and errors; es-modbus defaults it to `Modbus_Server`.
- `Unit_Map` / `create_handler(unit_map)`: the unit map and the es-modbus server handler, for callers that do not use descriptions (such as a controller) and assemble things themselves.
  - `attach_unit(unit_id, block, { start, offset, readonly })` places a block at byte `start` of a unit, from byte `offset` of the block; the options and each of them are optional. `start` and `offset` default to 0 and must be even non-negative integers, and `offset` below the size of the block, or it throws a `RangeError`. `readonly` (section 3) is `none` (the default), `all` for the whole block, or a non-empty list of distinct tag names of the layout of the block; another value throws a `RangeError`. The byte ranges of the blocks of one unit may not overlap: an overlap throws an `Error` that names both blocks.
  - `set_endian(unit_id, endian)` sets the byte order of a unit (section 3), which is `BE` until it is set; a unit id out of 0..255 or a byte order other than the four of section 2 throws a `RangeError`.
  - `get_endian(unit_id)`: gets the byte order of a unit.
  - `set_unmapped_read(unit_id, value)` / `set_unmapped_write(unit_id, value)` set how a unit answers the reads and the writes of its unmapped addresses (section 3): `zero` (the default) or `refuse` for reads, `ignore` (the default) or `refuse` for writes; a unit id out of 0..255 or another value throws a `RangeError`. `get_unmapped_read(unit_id)` / `get_unmapped_write(unit_id)` get them. Like `set_endian`, they may be called before or after the blocks of the unit are attached.
  - `unit_ids`: the units that have a block, in the order of their first attachment.
  - `segments(unit_id)`: the byte ranges of a unit (`{ block, start, offset, end, readonly }`), sorted by `start`, empty for a unit without block; `readonly` is the declaration of the placement, `none`, `all` or the list of tag names.
  - `resolve(unit_id, byte)`: the block that holds a byte of a unit and the byte offset in it (`{ block, offset }`), or null for an unmapped byte.
  - The `start`, `offset` and `end` of `segments` and the offset returned by `resolve` count the bytes of the IO buffer of the block (section 3).
- `Ldata`, `Ltag`, `create_scope`, `get_scope`, `yaml`, `desc_file` and the types of layout-data that go with them (`Layout`, `Layout_Scope`, `Layout_Tag`, `Layout_Desc`, `Block_Desc`, `Description`, `Registration`, `Endian`, `Tag_Type`): the API of [layout-data](https://github.com/goosy/layout-data/blob/main/doc/spec-data-api.md) that callers use, forwarded as it is. `load`, layout lookup, `create_ldata`, `get_ldata`, `delete_ldata` and `io_index_table` are methods of a scope or a layout. The `load` of a scope takes compiled descriptions only: `yaml` and `desc_file` compile YAML text and a description file. The blocks are `Ldata` objects, so this package is the one place the callers take this API from: they do not depend on layout-data themselves, and the process has one copy of it, which the scopes need (two copies share no scope, and `get_scope` of one does not find the scopes of the other). The forwarded API follows the version of layout-data this package depends on.

### Events

The package reports its diagnostics as events and outputs nothing itself.

- The handler returned by `create_handler` is an `EventEmitter`:

  | Event | Payload | When |
  | --- | --- | --- |
  | `unmapped` | `{ kind, unit_id, addr, operation }` | a request that succeeds reads or writes an unmapped point |
  | `unmapped_limit` | `{ limit }` | the 1024th key of `unmapped` was emitted; no further `unmapped` is emitted |
  | `request_refused` | `{ kind, unit_id, addr, operation }` | a request is refused (section 3), for each point that causes the refusal |
  | `request_refused_limit` | `{ limit }` | the 1024th key of `request_refused` was emitted; no further `request_refused` is emitted |
  | `listener_error` | `{ block, error }` | a listener of a block (`change`, `write`, `access`) throws when a request is committed; the data stay written and the master gets a normal response |

  - The payload of `unmapped` and of `request_refused` names one point: `kind` is its data type, `"holding_register"` (FC 3 / 6 / 16), `"input_register"` (FC 4) or `"coil"` (FC 1 / 2 / 5 / 15: the handler has no discrete inputs, and es-modbus answers FC 2 with the coils); `addr` is its register or coil address; `operation` is `"read"` or `"write"`.
  - The points that cause a refusal are the read-only points a write request writes, and the unmapped points a request reaches in a unit that refuses them; the other points of the request are not emitted. A point is either mapped and read-only, or unmapped, which the caller tells apart with `unit_map.resolve`. The range of a refused request is in the request frame of `server_receive`.
  - Flood suppression: each of the two events is emitted once per key (kind, unit, address, operation), for at most 1024 keys, so a master that polls or scans does not flood the listeners. Each event counts its own 1024 keys: once they are used up, it emits its `_limit` event once and no further event, while the requests are answered and refused as before. A request may reach up to 2000 coils (FC 1 / 2 / 15), so it may take many keys at once. The keys of the two events never coincide: a read-only point is mapped, and an unmapped point emits one or the other by the option of its unit.

- The servers are es-modbus `Modbus_Server`s with its events: `start`, `stop`, `socket_connect` (socket), `socket_disconnect` (socket), `socket_error` (error), `error` (error), `handler_error` (error), `receive` (the request frame), `send` (the response frame). The factories add no listener. An `EventEmitter` throws an `error` event that has no listener, so a caller that uses the factories must listen to `error` of each server.
- A handler that throws, or returns invalid values (a batch read of the wrong length, a register value out of range), is reported by es-modbus as `handler_error`, and the master gets exception 0x04. A refusal (section 3) is not reported so.
- `Modbus_Emulator` is an `EventEmitter`. It forwards the event `<name>` of each server as `server_<name>` (`server_start`, `server_stop`, `server_socket_connect`, `server_socket_disconnect`, `server_socket_error`, `server_error`, `server_handler_error`, `server_receive`, `server_send`) with the payload `{ server }`, plus `socket`, `error` or `frame` when es-modbus passes one; `server.name` tells which service it comes from. It forwards the events of the handler with their names and payloads. It always listens to `error` of its servers and never emits `error` itself.
- `Modbus_Emulator` emits `warning` with `{ server, message }` for each diagnostic of a `load`: a service on a serial bus that answers unit 0 or units from 248 to 255 (section 3), once per service and kind; `message` starts with the `name` of the server. A service without `unit_ids` is checked again for the units a later load adds.

## 5. Description

The descriptions that `load` takes are specified in [spec-descriptions.md](spec-descriptions.md): a description of layout-data, written in a YAML 1.2 file or text and compiled by `desc_file` or `yaml`, with the root keys `units` and `servers` of this package. It gives the layouts and their item tables, the blocks, the units that place the blocks, and the services.

## 6. Distribution

- Published as an ES module library with the entry `modbus-emulator`. What is published is the bundle of the source (`dist/index.js`) with its type declarations.
- It depends on `layout-data` and `es-modbus`, which are not bundled and stay as `import`s in the bundle: the package is meant to be a dependency of other packages, and the application that uses it bundles them once.
- Node.js >= 20.11.
