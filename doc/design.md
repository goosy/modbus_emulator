# modbus-emulator Design

> Chinese edition: [design.zh-CN.md](design.zh-CN.md). Keep the two in sync.
> For the requirements, see [spec.md](spec.md). This document describes the implementation.

## 1. Source Files

| File | Responsibility |
| --- | --- |
| `src/index.js` | The public interface of the package, including the forwarded API of layout-data |
| `src/unit_map.js` | `Unit_Map` and the es-modbus server handler |
| `src/server.js` | `create_tcp_server`, `create_rtu_server` |
| `src/emulator.js` | `Modbus_Emulator`: loads the descriptions, builds blocks and services |
| `src/index.d.ts` | Type declarations of the public interface (hand-written) |

Dependencies:

- `layout-data` (layout scopes and Ldata): a runtime dependency that stays external. The Ldata objects of the blocks reach the callers: a copy bundled here would be a second copy next to the caller's own, with scopes of its own.
  - `src/index.js` forwards the part of its API that callers use (`export ... from "layout-data"`: `Ldata`, `Ltag`, `create_scope`, `get_scope`, `yaml`, `desc_file`; the types in `src/index.d.ts`), so callers import it from this package and have one copy in the process. The rest of the layout API is methods of the scope and layout objects, which need no forwarding.
- `es-modbus`: a runtime dependency that stays external. This package is a dependency of other packages and not an application, so it does not bundle it.
  - The application that uses it bundles it once, which drops the unused `Modbus_Client` and keeps one copy of the shared code and one `prebuilds` directory of the serial port bindings (they are found next to the bundle that holds them, in the `prebuilds` directory of es-modbus when it is installed as a package).
  - `Modbus_Server` is declared in `src/index.d.ts` as the small interface that callers use, because es-modbus has no declarations.
- Publishing: the package publishes `src` as is, with no build step. Bundling belongs to the application, so a bundle of this package would only join its own source files.

## 2. Unit_Map and the Handler

- `Unit_Map` keeps a private `Map` from unit id to the segments of the unit, so no unit is an own property of the instance. `attach_unit(unit_id, block, start, offset)` checks that `start` and `offset` are even non-negative integers, so a caller that assembles a unit map is protected like the emulator, and inserts the segment `{ block, start, offset, end: start + size - offset }` at its place by `start`. Before inserting, it checks that the segment overlaps neither neighbor: the segments of a unit are sorted and never overlap, so the neighbors are the only candidates. An overlap throws an `Error` naming both blocks, and the unit map is left unchanged. A unit can hold several Ldata.
- `resolve(unit_id, byte)` finds the last segment whose `start` is at most `byte` by binary search, and the byte is mapped when it is below the `end` of that segment. The handler looks every point up through it.
- `create_handler(unit_map)` returns the handler required by es-modbus, with snake_case method names: `get_holding_register`, `get_input_register`, `set_holding_register`, `get_coil` (used for both FC 1 and FC 2), `set_coil`, and the batch methods `get_holding_registers` / `get_input_registers` / `get_coils` / `set_holding_registers` / `set_coils`, which es-modbus calls once per FC 3 / FC 4 / FC 1 and FC 2 / FC 16 / FC 15 request instead of once per point. es-modbus uses no single-point read when the batch read exists; the single-point reads are kept for the callers of the handler. The handler is an `EventEmitter` (`Object.assign(new EventEmitter(), methods)`).
- Register `addr` maps to byte `addr * 2`, read with `read_bytes` of Ldata in big-endian. Coil `addr` maps to bit `addr % 8` of byte `addr >> 3`.
- Writes go through `write_bytes` / `write_bit` of Ldata, which detects the change after each write. The bytes of a Ldata are not reachable otherwise.
- FC 6 / FC 5 call the single-point writes: a register write is one `write_bytes` of two bytes, taken from a shared two-byte array, which `write_bytes` copies at once.
- An unmapped address reads as 0 / false and a write is ignored. It is emitted as `unmapped` once per (type, unit, address), to avoid flooding the listeners when polling. The reported addresses are kept in a set of at most 1024 entries (`MAX_UNMAPPED_REPORTS`): a master that scans the whole address space would otherwise grow it to 65536 x 3 x 256 entries. When the set is full, `unmapped_limit` is emitted once, and later addresses are neither emitted nor recorded.
- Requests are validated by es-modbus first. When the handler throws, exception 0x04 is answered and es-modbus emits `handler_error` on the server.
- A batch write splits the request into runs: consecutive points held by one block at consecutive offsets; an unmapped point is reported and skipped. The blocks reached are written in nested `transaction`s, the block of the highest address outermost, so the inner ones commit first and the events follow the addresses. Inside the innermost one, a register run is one `write_bytes`, and the coils are written with `write_bit`, one call per byte and value (the bits set and the bits cleared), so `access` names only the Bools written. A block reached twice joins one transaction.
- A batch read splits the request the same way and reads in the same nested transactions: a register run is one `read_bytes`, a coil one `read_bit`, so `access` names only the Bools read; an unmapped point reads as 0 / false. Each transaction gathers the `access` of its block and emits it once at its commit.
- When a write throws, every transaction rolls back and the error reaches es-modbus (0x04). `transaction` rethrows the first error thrown by a listener at its commit; the handler catches it once all the writes are done, emits it as `listener_error` with `{ block, error }`, and the other blocks still commit, so the master gets a normal response.

## 3. Services

- `create_tcp_server(unit_map, { host, port, rtu, unit_ids, handler, name })`: creates a `Modbus_Server` with the handler. `unit_id` comes from the `unit_ids` option, which defaults to `unit_map.unit_ids`. es-modbus copies it into a set at construction, so the list of a server is independent of the unit map from its creation: the default is the units of the map at that time, `attach_unit` never changes it, and only `set_unit_ids` of the server does. The unit map and the units a server answers are kept apart on purpose: the first is data, the second the configuration of the server. `rtu` is passed to the option of the same name in es-modbus. The `handler` option is built with `create_handler` when omitted.
- `Modbus_Emulator` builds one handler (`emulator.handler`) over its unit map at construction, and passes it to all its servers, of every load. The handler only looks things up in the unit map and has no other state, so sharing it makes the unmapped-address warning reported once across all the servers, not once per server. The handler depends on the unit map and keeps the set of reported addresses, so it cannot live at module level: several emulators in one process would share it by mistake.
- `create_rtu_server(path, unit_map, { baud_rate, parity, data_bits, stop_bits, unit_ids, handler, name })`: `unit_ids` is the same. `port` takes the serial port path, from which es-modbus selects the RTU transport. The parameters are checked at construction, but the port is opened only at `start()`, so construction needs no hardware.
- The factories add no listener to a server: its events are the ones of es-modbus, and its caller listens to them, `error` included.

## 4. Modbus_Emulator

- Construction: the constructor takes the scope name, `modbus_emulator` by default (`DEFAULT_SCOPE`), keeps the scope `get_scope(name) ?? create_scope(name)` as `scope` (the error of `create_scope` for a name that is not an identifier is thrown as it is), and creates the handler (section 3). It reads no description: the caller attaches its listeners, then calls `load`.
- Reading: `load(sources)` takes a source or a list of them. A source that is a string or a `URL` is a description file, read and compiled with `desc_file` of layout-data (YAML 1.2, with the files of its `imports`); its errors, which name the file already, are collected as they are, and a `TypeError` (a URL that is not a `file:` URL) is collected with its message. Another source is taken as a `Description`, compiled by the caller with `desc_file` or `yaml`; one without the object `layouts` or the list `blocks`, which every `Description` has, is an error (`not a description file or a Description`), and the `load` of the scope rejects any other object that is not a `Description`. The former object entry for the controller is dropped: such an object is compiled with `yaml(JSON.stringify(object))`. The blocks are the `blocks` of the `Description`, whose entries keep the keys of this package (`unit_id`, `start`, `offset`); `servers` is the root key of the `Description`, which keeps the other root keys as they are parsed. The `blocks` and `servers` lists are joined in the order of the sources, so a layout file is an item of the list like the others. With several sources an error of this package is prefixed by its source: the path of a file (a `file:` URL converted to its path), or `description #N` for a `Description`, as layout-data names the items of a list; the title of the error lists the sources the same way. A failed compilation ends the load, after every source is read: it gives no blocks to check. A load whose sources give neither blocks nor servers is an error. The entries are numbered after the blocks and the servers of the earlier loads (`blocks[this.blocks.size + i]`, `servers[this.servers.length + i]`), so the labels of the servers stay unique in the emulator. The size of a block is the `size` of the layout of its `Description` (`Description.layouts[entry.layout]`), which `desc_file` and `yaml` compile before anything is loaded and which is the size of the layout the scope will hold.
- Scope: the compiled descriptions of a load are given to one `load` call of the scope, which registers the layouts, reusing a layout of the same fingerprint and name, and creates the Ldata of the blocks, all or nothing; its errors are collected. This package keeps no table of its own: the reuse of layouts is the one of layout-data, within a scope.
- Validation collects all violations and throws them at once, in stages, all of them before the `load` of the scope, so that a failed load changes neither the emulator nor the scope. Reading: the sources that are neither files nor `Description`s, files that cannot be read and the errors of their compilation, among them those of the blocks layout-data checks (`name` given as a string, unique in its description, `layout` listed by the description). Entries: servers (unknown keys by protocol, protocol, port range, the serial settings of `rtu` with the values es-modbus accepts, a port already used by an earlier server of this load or of an earlier one, the format of `unit_ids`) and the keys of the blocks that belong to this package (unknown keys, `unit_id` range, even `start` and `offset`); an error of a block ends the load here, as such a block cannot be placed. Placement: the blocks are placed on a temporary `Unit_Map`, which first takes the segments of the unit map of the emulator, then `{ name, size }` for each block of the load, so the overlap is the error of `attach_unit` (prefixed by the block entry) and no second overlap check is written; a block name of the emulator is an error (layout-data checks the names within a layout and within a call only, and `blocks` is keyed by name); and each unit of `unit_ids` must have a block on the temporary map. Loading: the errors of the `load` of the scope (a layout in conflict with one of the scope, a block name used by an ldata of its layout or given in two descriptions), which is the last step that may fail and is all or nothing itself. The errors of the placement come before those of loading, never in the same throw.
- After the `load` of the scope nothing fails. It creates one Ldata per block, which the emulator attaches to the unit map and adds to `blocks` in the order of the entries, and whose names it records as held (the names `stop()` gives back). The `layouts` of the result are added to `layouts`. Then each server without `unit_ids` of the earlier loads gets `set_unit_ids(unit_map.unit_ids)`, since the factories copy the units of the map at the creation of a server: so "every unit" follows the loads. One `Modbus_Server` is created per service of the load, all sharing the same unit map; its address is recorded for the port check of the later loads, and a server without `unit_ids` is recorded for the update above. `load` returns the blocks and the servers it added. It is synchronous and starts no server.
- `start(options)` throws when the emulator has no server. It starts the servers not yet started, which the emulator records: es-modbus restarts a running server on `start()` (it closes its connections and its listener or port, then opens them again), so `start()` is not called on the running ones. It starts them in parallel and waits with `Promise.allSettled` until each has a result, then handles the failures. It relies on these behaviors of es-modbus: the `start` / `stop` calls of a server are queued; `stop()` runs after an earlier `start` ends and never rejects; `stop()` on a server never started returns at once; `start()` on a running server stops it first. So by default a failure calls `stop()` on all services, including those that were running before the call, and then throws. With `partial` the started services are left running. Both modes throw the same `AggregateError`, so a failure is never silent; they differ only in whether the other services are stopped.
- The label of a service, its place in the descriptions loaded (`servers[i]`, prefixed by its source when a load has several) and its address (`modbus://host:port`, `rtu://host:port`, `serial://path`), is given to its server as the `name` option of es-modbus. The server carries it from then on: the errors of `start()` and the listeners of the forwarded events read `server.name`, and the emulator keeps no list of labels of its own.
- `stop()` stops all services in parallel with `Promise.all`, forgets which ones were started, then gives the names it holds back to their layouts (`block.layout.delete_ldata(name)`). Only the held names are given back, never a name the emulator gave back earlier: another emulator may hold it since. The Ldata keep working and stay in `blocks`, so `start()` serves them again; their names are free for another emulator of the same layouts in the scope.
- Events: `Modbus_Emulator` extends `EventEmitter`. After creating a server, it subscribes to the es-modbus events of the server and re-emits each `<name>` as `server_<name>` with `{ server }` plus the `socket`, `error` or `frame` argument; it subscribes to the events of the handler and re-emits them unchanged. Its listener of `error` keeps an error of a server from throwing, and it emits no `error` of its own, so an emulator without listeners never throws from an event.
- The diagnostics of a load are emitted as `warning` with `{ server, message }`: the caller attached its listeners after the construction. Each server of the load whose protocol is not `tcp` (es-modbus treats unit 0 as the broadcast address when the protocol is not `tcp`) is checked for unit 0 and units 248 to 255 among the units it answers (its `unit_ids`, or every unit of the map), and each earlier server without `unit_ids` among the units the load added, with one warning per server and kind; the message starts with the name of the server.

## 5. Build and Test

- `pnpm test`: runs `node --test`. The tests import `src`, which is what the package publishes; one test imports the package by its own name, to check that `exports` resolves to `src`. The tests use the es-modbus `Modbus_Client` as the master. The TCP servers under test listen on port 0 and the tests read the port the system picked, so no other process can take it between probing and listening. The RTU serial port is tested for construction only.
- `pnpm lint`: ESLint.
