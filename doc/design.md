# modbus-emulator Design

> Chinese edition: [design.zh-CN.md](design.zh-CN.md). Keep the two in sync.
> For the requirements, see [spec.md](spec.md). This document describes the implementation.

## 1. Source Files

| File | Responsibility |
| --- | --- |
| `src/index.js` | The public interface of the package, including the forwarded API of layout-data |
| `src/unit_map.js` | `Unit_Map` and the es-modbus server handler |
| `src/server.js` | `create_tcp_server`, `create_udp_server`, `create_rtu_server` |
| `src/emulator.js` | `Modbus_Emulator`: loads the descriptions, builds blocks and services |
| `src/index.d.ts` | Type declarations of the public interface (hand-written) |
| `dist/index.js` / `dist/index.d.ts` | The bundle of `src/index.js` and a copy of `src/index.d.ts`, generated by the build (`rolldown.config.js`, section 5); the published files; not committed |

Dependencies:

- `layout-data` (layout scopes and Ldata): a runtime dependency that is not bundled. The Ldata objects of the blocks reach the callers: a copy bundled here would be a second copy next to the caller's own, with scopes of its own.
  - `src/index.js` forwards the part of its API that callers use (`export ... from "layout-data"`: `Ldata`, `Ltag`, `create_scope`, `get_scope`, `yaml`, `desc_file`; the types in `src/index.d.ts`), so callers import it from this package and have one copy in the process. The rest of the layout API is methods of the scope and layout objects, which need no forwarding.
- `es-modbus`: a runtime dependency that is not bundled. This package is a dependency of other packages and not an application, so it does not bundle it.
  - The application that uses it bundles it once, which drops the unused `Modbus_Client` and keeps one copy of the shared code and one `prebuilds` directory of the serial port bindings (they are found next to the bundle that holds them, in the `prebuilds` directory of es-modbus when it is installed as a package).
  - `Modbus_Server` is declared in `src/index.d.ts` as the small interface that callers use, because es-modbus has no declarations.
- Publishing: the package publishes the bundle of its own source files, in which the dependencies stay as `import`s (section 5).

## 2. Unit_Map and the Handler

- `Unit_Map` keeps a private `Map` from unit id to the segments of the unit, so no unit is an own property of the instance. `attach_unit(unit_id, block, { start, offset, readonly })` checks that `unit_id` is an integer from 0 to 255, that `start` and `offset` are even non-negative integers, that `offset` is below `block.size`, so that no segment is empty, and that `readonly` is valid (`readonly_errors`, below), so a caller that assembles a unit map is protected like the emulator, and inserts the segment `{ block, start, offset, end: start + size - offset, readonly }` at its place by `start`; a list of tag names is copied and frozen. Before inserting, it checks that the segment overlaps neither neighbor: the segments of a unit are sorted and never overlap, so the neighbors are the only candidates. An overlap throws an `Error` naming both blocks, and the unit map is left unchanged. A unit can hold several Ldata.
- A second private `Map` keeps the byte order of each unit set by `set_endian`; `get_endian` returns `BE` for a unit not in it. `set_endian` checks the unit id (an integer from 0 to 255) and the order against its own list `ENDIANS` (`check_endian` of layout-data is internal), and throws a `RangeError`. It may be called before or after the blocks of the unit are attached, and does not make a unit without block one of `unit_ids`, which stays the units that have a segment. `set_unmapped_read` / `set_unmapped_write` keep the option of each unit in two more private `Map`s the same way, checked against `UNMAPPED_READS` (`zero`, `refuse`) and `UNMAPPED_WRITES` (`ignore`, `refuse`); the getters return the first value of the list for a unit not in them.
- Read-only mask of a segment: a segment declared read-only has a mask of the size of its block, in the bytes of the block (big-endian, not the IO order), kept in a second `WeakMap` of the module keyed by the segment, like the tables; a segment declared `none` has none. `attach_unit` builds it from `readonly`: every byte `0xff` for `all`; for a list, each item of `block.layout.items` it names marks bit `offset % 8` of byte `offset >> 3` when it is a Bool (`length` 1), and every bit of the bytes `offset >> 3` to `(offset + length - 1) >> 3` otherwise. The mask is in the bytes of the block, so it is the same for every byte order, and the handler reads it at the block offset it computed for the point. `readonly_errors(readonly, layout)` lists the violations of a declaration against a layout (not `none`, `all` or a list; an empty list; a name that is not a string or not an item of the layout; a name given twice); `attach_unit` throws the first one as a `RangeError`, and the emulator collects all of them.
- Byte order of a segment: a segment of a unit whose order is not `BE` has a table from the bytes of the IO buffer of its block to the bytes of the block, `io_to_block[j]`, the inverse of `block.layout.io_index_table(endian)`. The tables are kept in a `WeakMap` of the module keyed by the segment, so `segments()` keeps the shape of the spec; a `BE` segment has no table, and its IO bytes are the bytes of the block. `attach_unit` builds the table for the order of the unit, and `set_endian` rebuilds the tables of every segment of the unit. A table depends only on the layout and the order, which do not change while a block is served, so it is computed once and the handler never converts the data of a block as a whole: no copy of the IO buffer is kept, and a write of the caller through Ldata needs no synchronization.
- `resolve(unit_id, byte)` finds the last segment whose `start` is at most `byte` by binary search, and the byte is mapped when it is below the `end` of that segment; the offset it returns is the IO offset `byte - start + offset`. The handler looks every point up through the same search, and takes the table of the segment with it.
- `create_handler(unit_map)` returns the handler required by es-modbus, with snake_case method names: `get_holding_register`, `get_input_register`, `set_holding_register`, `get_coil` (used for both FC 1 and FC 2), `set_coil`, and the batch methods `get_holding_registers` / `get_input_registers` / `get_coils` / `set_holding_registers` / `set_coils`, which es-modbus calls once per FC 3 / FC 4 / FC 1 and FC 2 / FC 16 / FC 15 request instead of once per point. es-modbus uses no single-point read when the batch read exists; the single-point reads are kept for the callers of the handler. The handler is an `EventEmitter` (`Object.assign(new EventEmitter(), methods)`).
- Register `addr` maps to the IO byte `addr * 2` of the unit, coil `addr` to bit `addr % 8` of the IO byte `addr >> 3`. A layout is a whole number of registers (layout-data), and every byte order maps the two IO bytes of a register to the two bytes of one register of the block, in order or swapped: so a register is a pair of block bytes at `min(io_to_block[j], io_to_block[j + 1])`, swapped when `io_to_block[j]` is the higher one, read with `read_bytes` and decoded big-endian, or little-endian when swapped. A coil is bit `addr % 8` of the block byte `io_to_block[j]`; the bit mask is the same, as no byte order moves a bit inside its byte.
- Writes go through `write_bytes` / `write_bit` of Ldata, which detects the change after each write. The bytes of a Ldata are not reachable otherwise.
- FC 6 / FC 5 call the single-point writes: a register write is one `write_bytes` of two bytes, taken from a shared two-byte array, which `write_bytes` copies at once; a coil write is one `write_bit`. The write runs in a `transaction` of its block, like a batch write, so a listener error at its commit is emitted as `listener_error` (below), not thrown to es-modbus.
- Admission: before a request reads or writes anything, the handler locates all its points and sorts out the unmapped ones and, for a write, the read-only ones: a register is read-only when either of its two block bytes has a bit in the mask, a coil when its bit is in the mask. The points that cause a refusal are the read-only points and, when the unit refuses unmapped points for the operation (`get_unmapped_read` / `get_unmapped_write` of the unit map), the unmapped ones, in the order of the addresses. When there are any, each is emitted as `request_refused` and the handler throws a `Modbus_Exception(0x02)` of es-modbus, so nothing is read or written and no `unmapped` is emitted; otherwise the unmapped points are emitted as `unmapped` and the request goes on. The single-point methods (FC 5 / FC 6, and the single reads kept for the callers) are admitted the same way with one point.
- Flood suppression: `unmapped` and `request_refused` are each emitted through a reporter of its own (`create_reporter(event, limit_event)`), which emits an event once per key `kind:unit_id:addr:operation`. The keys are kept in a set of at most 1024 entries (`MAX_REPORTS`): a master that scans the whole address space would otherwise grow it to 65536 x 3 x 256 x 2 entries. When the set is full, the limit event is emitted once, and later keys are neither emitted nor recorded. Each event has its own set and its own limit, so the unmapped reads of a scan cannot use up the keys of the refusals.
- Requests are validated by es-modbus first. When the handler throws, exception 0x04 is answered and es-modbus emits `handler_error` on the server, except for an error carrying an allowed `exception_code`, such as the `Modbus_Exception` of a refusal, which is answered with that code and emits nothing. A broadcast on a serial bus calls the handler without answering, so a refused broadcast writes nothing and still emits `request_refused`.
- A batch write splits the request into runs: consecutive points held by one block at consecutive block offsets, the registers of a run all swapped or all in order; an unmapped point belongs to no run (it is reported or refused by the admission above). With `BE` and `BEBS` the registers of a block are in the order of the addresses, so a request is one run per block as before; with `LE` and `LEBS` the two registers of a 4-byte value are in reverse order, so they are separate runs of the same block. The blocks reached are written in nested `transaction`s, the block of the highest address outermost, so the inner ones commit first and the events follow the addresses. Inside the innermost one, a register run is one `write_bytes`, and the coils are written with `write_bit`, one call per byte and value (the bits set and the bits cleared), so `access` names only the Bools written. A block reached twice joins one transaction.
- A batch read splits the request the same way and reads in the same nested transactions: a register run is one `read_bytes`, a coil one `read_bit`, so `access` names only the Bools read; an unmapped point reads as 0 / false. Each transaction gathers the `access` of its block and emits it once at its commit.
- When a write throws, every transaction rolls back and the error reaches es-modbus (0x04). `transaction` rethrows the first error thrown by a listener at its commit; the handler catches it once all the writes are done, emits it as `listener_error` with `{ block, error }`, and the other blocks still commit, so the master gets a normal response.

## 3. Services

- `create_tcp_server(unit_map, { host, port, rtu, unit_ids, handler, name })`: creates a `Modbus_Server` with the handler. `unit_id` comes from the `unit_ids` option, which defaults to `unit_map.unit_ids`. es-modbus copies it into a set at construction, so the list of a server is independent of the unit map from its creation: the default is the units of the map at that time, `attach_unit` never changes it, and only `set_unit_ids` of the server does. The unit map and the units a server answers are kept apart on purpose: the first is data, the second the configuration of the server. `rtu` selects the transport option of es-modbus, `rtu_over_tcp` instead of `tcp`, which takes the `host:port` target, an IPv6 host in brackets. The `handler` option is built with `create_handler` when omitted.
- `create_udp_server(unit_map, { host, port, rtu, unit_ids, handler, name })` is the same with the transport options `udp` and `rtu_over_udp`: both factories share one function that checks the options and builds the target, and differ only in the transport option they give it.
- `Modbus_Emulator` builds one handler (`emulator.handler`) over its unit map at construction, and passes it to all its servers, of every load. The handler only looks things up in the unit map and has no other state, so sharing it makes the unmapped-address warning reported once across all the servers, not once per server. The handler depends on the unit map and keeps the set of reported addresses, so it cannot live at module level: several emulators in one process would share it by mistake.
- `create_rtu_server(path, unit_map, { baud_rate, parity, data_bits, stop_bits, unit_ids, handler, name })`: `unit_ids` is the same. `port` takes the serial port path, from which es-modbus selects the RTU transport. The parameters are checked at construction, but the port is opened only at `start()`, so construction needs no hardware.
- The factories add no listener to a server: its events are the ones of es-modbus, and its caller listens to them, `error` included.

## 4. Modbus_Emulator

- Construction: the constructor takes the scope name, `modbus_emulator` by default (`DEFAULT_SCOPE`), keeps the scope `get_scope(name) ?? create_scope(name)` as `scope` (the error of `create_scope` for a name that is not an identifier is thrown as it is), and creates the handler (section 3). It reads no description: the caller attaches its listeners, then calls `load`.
- Reading: `load(sources)` takes a source or a list of them. A source that is a string or a `URL` is a description file, read and compiled with `desc_file` of layout-data (YAML 1.2, with the files of its `imports`); its errors, which name the file already, are collected as they are, and a `TypeError` (a URL that is not a `file:` URL) is collected with its message. Another source is taken as a `Description`, compiled by the caller with `desc_file` or `yaml`; one without the object `layouts` or the list `blocks`, or with a block entry that is not a mapping naming a layout of its `layouts`, as every `Description` has them, is an error (`not a description file or a Description`), and the `load` of the scope rejects any other object that is not a `Description`. The former object entry for the controller is dropped: such an object is compiled with `yaml(JSON.stringify(object))`. The blocks are the `blocks` of the `Description`; `units` and `servers` are root keys of the `Description`, which keeps the other root keys as they are parsed, and each of them that is given must be a list. The `blocks`, `units` and `servers` lists are joined in the order of the sources, so a layout file is an item of the list like the others. With several sources an error of this package is prefixed by its source: the path of a file (a `file:` URL converted to its path), or `description #N` for a `Description`, as layout-data names the items of a list; the title of the error lists the sources the same way. A failed compilation ends the load, after every source is read: it gives no blocks to check. A load whose sources give neither blocks nor servers is an error. The entries are numbered after the blocks, the units and the servers of the earlier loads (`blocks[this.blocks.size + i]`, `units[this.unit_map.unit_ids.length + i]`, as every unit entry loaded is one unit with a block, `servers[this.servers.length + i]`), so the labels of the servers stay unique in the emulator. A unit entry is read with the blocks of its own `Description`, by name, so that it places only those. The size of a block is the `size` of the layout of its `Description` (`Description.layouts[entry.layout]`), which `desc_file` and `yaml` compile before anything is loaded and which is the size of the layout the scope will hold.
- Scope: the compiled descriptions of a load are given to one `load` call of the scope, which registers the layouts, reusing a layout of the same fingerprint and name, and creates the Ldata of the blocks, all or nothing; its errors are collected. This package keeps no table of its own: the reuse of layouts is the one of layout-data, within a scope.
- Validation collects all violations and throws them at once, in stages, all of them before the `load` of the scope, so that a failed load changes neither the emulator nor the scope. Reading: the sources that are neither files nor `Description`s, files that cannot be read and the errors of their compilation, among them those of the blocks layout-data checks (`name` given as a string, unique in its description, `layout` listed by the description). Entries: servers (unknown keys by protocol, protocol, port range, the serial settings of `rtu` with the values es-modbus accepts, a port already used by an earlier server of this load or of an earlier one (the ports in use are keyed by the TCP address, the UDP address prefixed by `udp `, or the serial port path, so a UDP port never conflicts with a TCP one), the format of `unit_ids`), the block entries (a key other than `name` and `layout`) and the units (unknown keys of a unit entry and of a placement, `unit_id` range, a `unit_id` given twice in the load or a unit of the emulator, `endian` one of the four orders, `unmapped_read` and `unmapped_write` one of their values, `blocks` a non-empty object, even `start` and `offset`, an `offset` not below the size of the block, a block name that is not a block of the description of the unit, a block placed twice, a block of a description placed by no unit of it, and the errors `readonly_errors` lists for `readonly` against the layout of the block in its `Description`); an error of an entry ends the load here, as its blocks cannot be placed. Placement: the blocks are placed on a temporary `Unit_Map`, which first takes the segments of the unit map of the emulator, then `{ name, size }` for each placement of the load, in the order of the unit entries, so the overlap is the error of `attach_unit` (prefixed by the placement, `units[i].blocks.<name>`) and no second overlap check is written; `readonly` is not given to the temporary map, which only places; the temporary map sets no byte order, which does not change the byte ranges and needs the layout of a real block; a block name of the emulator is an error (layout-data checks the names within a layout and within a call only, and `blocks` is keyed by name); and each unit of `unit_ids` must have a block on the temporary map. Loading: the errors of the `load` of the scope (a layout in conflict with one of the scope, a block name used by an ldata of its layout or given in two descriptions), which is the last step that may fail and is all or nothing itself. The errors of the placement come before those of loading, never in the same throw.
- After the `load` of the scope nothing fails. It creates one Ldata per block, which the emulator adds to `blocks` in the order of the block entries, and whose names it records as held (the names `stop()` gives back). Then, for each unit entry in order, it sets the byte order of the unit (`set_endian`, when `endian` is given) and its `unmapped_read` / `unmapped_write` when given, and attaches its blocks in the order of its placements with their `readonly`, so the tables and the masks of the segments are built once, at their attachment. The `layouts` of the result are added to `layouts`. Then each server without `unit_ids` of the earlier loads gets `set_unit_ids(unit_map.unit_ids)`, since the factories copy the units of the map at the creation of a server: so "every unit" follows the loads. One `Modbus_Server` is created per service of the load, all sharing the same unit map; its address is recorded for the port check of the later loads, and a server without `unit_ids` is recorded for the update above. `load` returns the blocks and the servers it added. It is synchronous and starts no server.
- `start(options)` throws when the emulator has no server. It starts the servers not yet started, which the emulator records: es-modbus restarts a running server on `start()` (it closes its connections and its listener or port, then opens them again), so `start()` is not called on the running ones. It starts them in parallel and waits with `Promise.allSettled` until each has a result, then handles the failures. Before it starts any of them, it checks every block of the emulator: a block whose layout holds its name for another Ldata (`layout.get_ldata(name)` returns another Ldata; it throws for a name not held, which is no conflict) is a conflict; with any conflict it throws an `Error` whose `errors` lists them all, before any service is started and any name is bound, and otherwise binds each name that is not held back to its layout (`layout.add_ldata(block)`, layout-data 0.7.0) and records it as held. It relies on these behaviors of es-modbus: the `start` / `stop` calls of a server are queued; `stop()` runs after an earlier `start` ends and never rejects; `stop()` on a server never started returns at once; `start()` on a running server stops it first. So by default a failure calls `stop()` on all services, including those that were running before the call, and then throws; it stops the services only, not the emulator: the names stay held, and only the `stop()` of the caller gives them back. With `partial` the started services are left running. Both modes throw the same `AggregateError`, so a failure is never silent; they differ only in whether the other services are stopped.
- The label of a service, its place in the descriptions loaded (`servers[i]`, prefixed by its source when a load has several) and its address (`modbus://host:port`, `rtu://host:port`, `modbus+udp://host:port`, `rtu+udp://host:port`, `serial://path`), is given to its server as the `name` option of es-modbus. The server carries it from then on: the errors of `start()` and the listeners of the forwarded events read `server.name`, and the emulator keeps no list of labels of its own.
- `stop()` stops all services in parallel with `Promise.all`, forgets which ones were started, then gives the names it holds back to their layouts (`block.layout.delete_ldata(name)`). Only the held names are given back, never a name the emulator gave back earlier: another emulator may hold it since. The Ldata keep working and stay in `blocks`, so `start()` binds their names back and serves them again; until then their names are free for another emulator of the same layouts in the scope.
- Events: `Modbus_Emulator` extends `EventEmitter`. After creating a server, it subscribes to the es-modbus events of the server and re-emits each `<name>` as `server_<name>` with `{ server }` plus the `socket`, `error` or `frame` argument; it subscribes to the events of the handler and re-emits them unchanged. Its listener of `error` keeps an error of a server from throwing, and it emits no `error` of its own, so an emulator without listeners never throws from an event.
- The diagnostics of a load are emitted as `warning` with `{ server, message }`: the caller attached its listeners after the construction. Each server of the load whose protocol is neither `tcp` nor `udp` (es-modbus treats unit 0 as the broadcast address when the protocol has no MBAP frames) is checked for unit 0 and units 248 to 255 among the units it answers (its `unit_ids`, or every unit of the map), and each earlier server without `unit_ids` among the units the load added, with at most one warning per server and kind in each load, so a unit is warned once per server; the message starts with the name of the server.

## 5. Build and Test

- `pnpm build`: `rolldown -c`. `rolldown.config.js` empties `dist` when it is loaded and bundles `src/index.js` into `dist/index.js` (`platform: "node"`, `format: "es"`, one file). `external` is the names of the `dependencies` of `package.json` (and their subpaths) and the built-in modules with the `node:` prefix, so `layout-data` and `es-modbus` stay `import`s in the bundle. A plugin of the configuration emits `src/index.d.ts` unchanged as `dist/index.d.ts`, as the declarations are hand-written and refer to no other file of the package.
- Publishing: the `files` of `package.json` are `dist` and `CHANGELOG.md`; the `default` of `exports` points to `dist/index.js` and `types` to `dist/index.d.ts`. `prepare` runs the build, so the bundle exists after an install from the repository or the workspace and before packing.
- `pnpm test`: builds first, then runs `node --test` (every test, against `src`) and `pnpm test:dist` (every test again, against the bundle). The tests use the public interface only and take it from `test/target.js`: the entry of `src` by default, or the package by its own name, that is the bundle in `dist`, when `test/dist.js` is imported first (`node --test --import ./test/dist.js`), which sets the environment variable `MODBUS_EMULATOR_TEST_TARGET=dist` for the processes of the test files. The bundling test (`test/bundle_test.js`) checks that `exports` points to the files of `dist`, that the bundle exports the names of the entry of `src`, and that its `import`s are only `layout-data`, `es-modbus` and `node:` modules. The tests use the es-modbus `Modbus_Client` as the master. The TCP servers under test listen on port 0 and the tests read the port the system picked, so no other process can take it between probing and listening. es-modbus does not accept port 0 in its options, so a test builds the server with a fixed port, then sets its `port` to 0 before `start()` (`ephemeral` in `test/helpers.js`), as the tests of es-modbus do. The UDP servers under test bind port 0 the same way, and the tests read the port from the bound UDP socket of the server (`listening_port` in `test/helpers.js`). The RTU serial port is tested for construction only.
- `pnpm lint`: ESLint.
